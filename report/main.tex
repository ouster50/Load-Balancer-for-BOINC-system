\section*{Аннотация}   % this is how to use russian
При проектировании высокопроизводительных и распределенных систем одной из важнейших задач является выбор и настройка системы выдачи заданий (балансировщик нагрузки). При использовании гомогенных вычислительных узлов в кластере можно использовать готовые решения (slurm, torque и др.), но в гетерогенных системах готовые решения не будут работать из коробки. В распределенных системах из-за большой гетерогенности и других ограничений может возникнуть потребность разработки оригинального планировщика заданий. В распределенной вычислительной системе в качестве части ресурсов могут быть использованы облачные ресурсы или ресурсы кластеров. Уже были разработаны решения (к примеру, CluBoRun в грид-системе на платформе BOINC) по использованию ресурсов кластера в фоновом режиме. Предлагается разработать /модифицировать систему выдачи заданий для грид-системы на платформе BOINC, в которой присутствуют сегменты кластеров.

\section{Введение} 
\subsection{Описание предметной области}
Предметная область проекта охватывает распределенные системы с гетерогенной инфраструктурой с основными компонентами:
\begin{itemize}
    \item BOINC (Berkeley Open Infrastructure for Network Computing) — платформа для добровольных вычислений, объединяющая ресурсы разнородных устройств (серверов, кластеров, персональных компьютеров) в единую сеть
    \item Кластеры — узлы, интегрированные в распределенную систему с целью повышения доступности
    \item Гетерогенные ресурсы — устройства с различными характеристиками: вычислительной мощностью, объемом памяти, доступностью и другими
    \item Балансировщик нагрузки — компонент, отвечающий за распределение вычислительных задач между узлами с учетом их возможностей и текущих состояний
\end{itemize}
Также предметная область имеет следующие особенности:
\begin{itemize}
    \item Отсутствие централизованного контроля за узлами системы
    \item Разнородность ресурсов каждого из узлов
    \item Различные режимы работы узлов (не все устройства доступны на протяжении 100\% времени)
    \item Различный объем задач, время выполнения которых может варьироваться от нескольких минут до нескольких дней
    \item Необходимость минимизации накладных расходов для балансировщика
\end{itemize}

\subsection{Релевантность и значимость}
Актуальность данного проекта обусловлена множеством существующих на данный момент проблем, таких как:
\begin{enumerate}
    \item Современные вычислительные задачи такие, как анализ больших данных, биоинформатика, требуют огромного количества ресурсов, что способствует росту числа гетерогенных распределенных систем
    \item Стандартные планировщики задач оптимизированы под гомогенные системы и не учитывают различия в производительности узлов и их доступность, что в гетерогенных системах приводит к простаиванию некоторых узлов или, наоборот, излишней загруженности отдельных
    \item Необходимость развития динамических алгоритмов балансировки в противовес сущестующим решениям с их статическими правилами
    \item Оптимизация всех вычислений, выполняющихся на платформе BOINC
\end{enumerate}

\subsection{Цели и задачи}
Целью данного проекта является разработка системы выдачи заданий для распределенной системы на платформе BOINC. Для ее достижения необходимо было выполнить следующие задачи:
\begin{enumerate}
    \item Обзор систем балансировки нагрузки для кластеров и распределенных систем
    \item Выбор системы моделирования и адаптация модели под специфику гибридной распределенной системы
    \item Реализация/модификация системы балансировки нагрузки гибридной распределенной системы
    \item Тестирование системы балансировки на модели гибридной распределенной системы
    \item Анализ полученных результатов
\end{enumerate}

\subsection{Предполагаемые результаты проекта}
\begin{enumerate}
    \item Подробное описание методики моделирования гибридной распределенной системы
    \item Подробное описание системы балансировки нагрузки гибридной распределенной системы
    \item Анализ результатов моделирования системы
    \item Подготовка подробного отчета о проделанной работе и проведенном тестировании
\end{enumerate}

\section{Литературный обзор}
\subsection{Обзор предметной области}
В своем начале Интернет имел очень мало потребителей, так что любой сервер мог выдерживать нагрузку даже самого популярного сайта, к тому же его падение не стало бы большой проблемой. Со временем люди были вынуждены заняться вопросами масштабирования ввиду растущей нагрузки. И если сначала проблема решалась увеличением числа процессоров, их улучшением, увеличением объема оперативной памяти, то после стало понятно, что есть потолок такого вертикального масштабирования, так что появилось понятие балансировки нагрузки.~\cite{srv-lb}

В общем случае, порядок работы балансировщика такой:
\begin{enumerate}
    \item Получение входящих запросов от различных клиентов
    \item Расчет размера входящих запросов и формирование очереди запросов
    \item Периодическая проверка состояния серверов в пуле с помощью системы мониторинга
    \item Использование стратегии / алгоритма / эвристики для выбора подходящего сервера под каждый входящий запрос
\end{enumerate}

Сама идея балансировки нагрузки вносит в систему большое количество преимуществ:

\begin{enumerate}
    \item Упрощенное отслеживания трафика
    \item Улучшенное использование ресурсов
    \item Балансировка нагрузки на сеть на основании загруженности серверов
    \item Улучшенная доступность ресурсов
    \item Уменьшение избыточного потребления ресурсов
\end{enumerate}~\cite{lb-in-cloud}

Решения проблемы балансировки нагрузки делятся на 2 основных подхода в зависимости от того, принимает ли алгоритм решения на основе текущего состояния системы или нет: статический и динамический.

Статический подход предполагает наличие знаний о статусе системы, требованиях к ресурсам, времени связи и другим показателям. Балансировка при таком подходе достигается путем создания связей между списком процессоров и списком задач таким образом, чтобы достигалась максимальная производительность. Хотя назначения могут быть как детерминированными, так и вероятностными, текущее состояние системы не учитывается ни в одном из вариантов организации балансировки. Это существенный недостаток статических подходов, который оказывает существенное влияние на общую производительность из-за непредсказуемости колебаний нагрузки на систему. Некоторые методы, используемые при статической балансировке: перечисление и поиск в пространстве решений, теория графов, теория очередей.

При динамическом подходе, решения о балансировке нагрузки принимаются на основе текущего состояния системы; задачам разрешается динамически перемещаться с перегруженного узла на недостаточно загруженный узел для более быстрой обработки. Способность реагировать на изменения в системе является основным преимуществом динамического подхода к балансировке нагрузки. Хотя найти динамическое решение намного сложнее, чем статическое, динамическая балансировка нагрузки может повысить производительность за счет своей адаптивности. Далее сосредоточимся именно на таких подходах.

Механизм управления динамической балансировкой может быть распределенным, когда ответственность за балансировку распределяется между узлами, и нераспределенным, когда ответственность за балансировку лежит на одном или нескольких узлах; включает централизованный (один центральный узел управляет балансировкой всей системы) и полу распределенный (узлы делятся на кластеры с центральными узлами для балансировки внутри кластера) подходы.~\cite{lb-in-ds}

\subsection{Обзор существующих методов}
Рассмотрим методы балансировки нагрузки, применимые к распределённым вычислительным системам с акцентом на гибридные конфигурации (платформы типа BOINC + стабильные кластерные сегменты). Среди критериев для них можно выделить: простота мониторинга, устойчивость к churn (неконтролируемое подключение / отключение узлов), гетерогенность ресурсов, величина накладных расходов, масштабируемость. Всего можно выделить несколько групп подходов к балансировке нагрузки:

\begin{itemize}
    \item Классические статические методы (Round Robin, Random Strategy) — просты в мониторинге, однако не учитывают размер и время выполнения задач
    \item Классические динамические методы (Least-Connection) — также просты в мониторинге, но не учитывает общую нагрузку на узлы
    \item Адаптивные методы — балансировка происходит на основе метрик, вычисляемых в реальном времени; требуют постоянных вычислений
    \item Предиктивные ML подходы — планировщики, которые хорошо работают даже в сложных условиях, но требуют времени и данных для обучения модели~\cite{lb-adv}
    \item Существующие решения для BOINC (CluBoRun) — механизмы верификации, учета доступности, отслеживания churn и другие~\cite{boinc-lb}
\end{itemize}

Большинство классических и оптимизационных алгоритмов работают при допущении, что узлы доступны и их характеристики относительно стабильны. В средах типа BOINC это допущение неприменимо: изменчивость системы и разнородность устройств приводит к частому перераспределению задач между узлами. Если в гомогенных системах перенос задач - относительно стандартный процесс, в гибридных системах такой подход может привести к серьёзному росту накладных расходов из-за неоднородности устройств, поэтому в подобных системах правильным подходом считается исключение или сведение к минимум подобныз операций. Также нужно отметить, что для гибридных систем важно сохранять баланс между количеством собираемых метрик и их полезности для планировщика, что труднодостижимо при подходах с глобальным мониторингом узлов.~\cite{lb-in-cloud}

\subsection{Особенности BOINC}
Платформа BOINC использует модель \emph{client-initiated}: вычислительный узел сам запрашивает работу через RPC. Scheduler сканирует shared-memory массив feeder, оценивает совместимость workunit с host и ранжирует кандидатов по score. Назначенная задача не мигрирует на другой host до timeout или повторной репликации. Поле \texttt{rsc\_fpops\_est} задаёт оценку сложности, которая может расходиться с реальным временем выполнения - это важный источник ошибок для любой adaptive-политики. Решение CluBoRun~\cite{boinc-lb} интегрирует кластерные ресурсы в BOINC-проект, но не решает глобальную балансировку по классам устройств (кластер / desktop / mobile).

\subsection{Выводы из обзора}
\begin{itemize}
    \item На данный момент существует широкий набор методов балансировки, однако немногие работы систематически исследуют их поведение в гибридных системах

\subsection{Топология системы}
Тестовый стенд состоит из 6 хостов-устройств с различными характеристиками:
\begin{itemize}
    \item 2 кластерных элемента (4 CPU, 4 Gb RAM)
    \item 1 устройство ПК (2 CPU, 2 Gb RAM)
    \item 1 маломощный узел (1 CPU, 1 Gb RAM)
    \item 2 элемента - мобильных устройств (0.5 CPU 0.5 Gb RAM)
\end{itemize}

Каждое устройство представляет собой независимый вычислительный хост; с точки зрения технической реализации каждый хост - это отдельный \textbf{Docker} контейнер, который конфигурационно настроен под конкретное число CPU. Данный выбор хостов с их настройками был обусловлен следующими требованиями к тестовому стенду:

\begin{itemize}
    \item Стенд обязан содержать разнородные с точки зрения мощности устройства для моделирования гибридной среды
    \item Стенд обязан содержать как высокопроизводительные элементы (кластеры), так и низкопроизводительные (мобильные устройства)
    \item Стенд обязан иметь несколько одинаковых устройств для проверки балансировки нагрузки между однородными хостами (распределение задач между одинаковыми с точки зрения мощности клиентами)
\end{itemize}

\section{Подходы к тестированию системы и метрики качества}

\subsection{Эвристики распределения задач}

В литературе помимо классических подходов рассматриваются некоторые эвристики, которые были смоделированы в данном проекте для сравнения с разработанным методом:
\begin{itemize}
    \item LPT (Longest Processing Time first) - длинные задачи назначаются первыми; при нескольких параллельно работающих однотипных хостах снижает общее время работы, но может ухудшить качество распределения и среднее время отклика для коротких задач
    \item SJF (Shortest Job First) - короткие задачи получают приоритет; минимизирует среднее время отклика, но крупные задачи могут долго простаивать в очереди
\end{itemize}

Кластерные планировщики (Slurm, Torque) оптимизированы под гомогенные очереди с централизованным контролем и статическим планированием; они не учитывают pull-модель BOINC и отказы узлов, поэтому не применимы к гибридной системе, по этой причине они не попали в предметную область данного проекта. Таким образом, кроме алгоритма балансировки BOINC по умолчанию были добавлены в тестирование упомянутые выше LPT, SJF, а также классические подходы: Round Robin, Random и Weighted Least Loaded.

\subsection{Метрики оценки производительности}

Выбор метрик обусловлен необходимостью учета как общих показателей производительности, так и особенностей гетерогенной вычислительной среды.

\begin{itemize}
    \item Пропускная способность (Throughput) -- число выполненных задач за единицу времени. Формула: $T = \dfrac{N_{\text{completed}}}{\Delta t}$
    \item Время выполнения задачи -- среднее, перцентиль (95\%). Для каждой задачи $i$: $R_i = t^{(i)}_{\text{finish}} - t^{(i)}_{\text{arrival}}$. Среднее: $\overline{R} = \dfrac{1}{N}\sum_i R_i$
    \item Загруженность узлов -- для узла $j$: $u_j = \dfrac{\text{busy\_cpu\_time}_j}{\text{observation\_time}}$. Сводная метрика: коэффициент вариации $Load CV = \dfrac{\sigma(u_j)}{\overline{u}}$ (показывает балансировку)
    \item Общее время завершения набора задач -- $Makespan = \max_{i}\{t_{\text{finish}}\} - \min_{i}\{t_{\text{arrival}}\}$
    \item "Честность" распределения задач $Jain = \frac{(\sum_{i=1}^{n}x_i)^2}{n\cdot\sum_{i=1}^{n}x_i^2}$, где $x_i$ - число задач, выполненных узлом $i$
\end{itemize}

Такой набор метрик позволяет оценить как производительность системы, так и качество балансировки нагрузки в условиях гибридной среды.

\subsection{Процесс тестирования}

Система тестировалась в разных условиях для приближения к реальной жизни. Стенд позволяет настроить отказы некоторых хостов (моделирование churn), их длительность и частоту. Churn реализован через временную остановку контейнера, что допустимо при подобном локальном модеоировании системы. В рамках теста были смоделированы стабильная среда и среда с периодическими кратковременными отказами хостов. При каждом запуске автоматически вычислялись метрики качества для дальнейшего анализа, а также сохранялись текущие конфигурации системы для воспроизводимости результатов. Отметим про воспроизводимость, что в политике Random использовались псевдослучайные числа для детерменированного поведения системы от запуска к запуску (при равенстве основных параметров). Каждый раз прогонялись все политики, после чего метрики аггрегировались и анализировались в рамках оптимизации целевого алгоритма балансировки.

В качестве источника задач использовалось встроенное приложение BOINC $uppercase$, которое генерировало задачи разной сложности через параметр cpu\_time. Всего было 3 типа задач: short (cpu\_seconds=5), medium (cpu\_seconds=30), long (cpu\_seconds=120). Идея была не только оптимизировать распределение задач между узлами, чтобы все исполняли примерно одно количество задач, но и повысить честность такого распределения, а именно исполнение более тяжеловесных задач мощными узлами и наоборот - более легкие задачи оставлять маломощным узлам. Поэтому необходима описанная выше разнородность задач.

\section{Разработка алгоритма балансировки}

Прежде чем описывать разработанный алгоритм, необходимо зафиксировать, как именно работает штатный планировщик в BOINC, поскольку именно он выступает baseline в экспериментах и служит границей, ниже которой по метрикам опускаться неприемлемо.

\subsection{Планировщик BOINC по умолчанию}

BOINC использует pull-модель распределения задач: вычислительный узел самостоятельно инициирует RPC-запрос к планировщику и сообщает, сколько работы он готов принять (в секундах CPU, в числе задач или иначе). Планировщик не выбирает хост для задачи - он лишь отвечает на запрос данного клиента в данный момент. Назначенная задача не мигрирует на другой узел по достижении таймаута, при ошибке или при создания новой реплики. Это принципиально отличает BOINC от централизованных кластерных планировщиков (Slurm, Torque), где планироващик видит всю очередь задач и все узлы одновременно, и именно эти недостатки должны быть устранены или сведены к минимуму в рамках текущего проекта.

Очередь задач, доступная планировщику, - это не вся база данных, а кэш в памяти, который заполняет отдельный процесс под названием feeder. Он читает из БД информацю о задачах, готовых к отправке, и помещает их в массив фиксированного размера (по умолчанию до 100 слотов, параметр shmem\_work\_items задачется конфигурационно). Каждый элемент содержит метаданные задачи (оценку сложности rsc\_fpops\_est, требования к памяти и диску), приоритет реплики res\_priority и счётчик отказов infeasible\_count. Планировщик при каждом запросе клиента сканирует этот массив; порядок обхода начинается со случайного смещения, чтобы не застревать на одних и тех же задачах.

Для вычисления наиболее подходящего хоста вызывается функция $send\_work\_score()$, логика которой сводится к двум шагам:
\begin{enumerate}
    \item Сканирование и ранжирование - для каждого слота в shared memory подбирается совместимая версия приложения под платформу хоста, для каждой допустимой пары $(workunit, host)$ вычисляется score, после чего все кандидаты сортируются по score по убыванию
    \item Отправка - планировщик последовательно пытается выдать задачи из отсортированного списка, пока не исчерпан лимит RPC max\_wus\_to\_send, не превышены квоты max\_jobs\_in\_progress и пока хост ещё запрашивает работу
\end{enumerate}
Отдельный проход выполняется для каждого типа процессора (GPU-типы, затем CPU).

Прежде чем хост попадёт в ранжирование, он должен пройти дополнительные проверки:
\begin{itemize}
    \item Достаточно ли оперативной памяти и дискового пространства?
    \item Приложение входит в список, выбранный пользователем (хостом) в project preferences?
    \item Хост успеет завершить задачу до глобального дедлайна по ней?
\end{itemize}
Последняя проверка - ключевая для гетерогенной среды. Оценка длительности выполнения задачи:
\[
    \hat{t}_{ij} = \frac{\text{rsc\_fpops\_est}_i}{\text{projected\_flops}_j \cdot \text{available\_frac}_j},
\]
где available\_frac - доля времени, когда клиент реально доступен для BOINC. К этой оценке добавляется estimated\_delay - время, которое хост уже занят текущими задачами. Если $\hat{t}_{ij} + \text{estimated\_delay} > \text{delay\_bound}$, задача для данного хоста в score не попадает. Следствие: мощные и стабильные узлы забирают длинные задачи; слабые и малодоступные - только короткие или ничего.

Если быстрые проверки пройдены, выполняется slow\_check() с запросами в БД: нет ли уже результата этой задачи на данном хосте. Только после этого задача добавляется в ответ клиенту.

Оценка каждого хоста считается исходя из нескольких эвристик:
\begin{itemize}
    \item Reliability - задача с need\_reliable=true и высоким приоритетом отправляется только на хосты с подходящим уровнем приложения
    \item LTT - для high-priority workunits в режиме batch acceleration задачи идут только на LTT-хосты
    \item Locality - бонус, если входные данные задачи уже есть на хосте
    \item res\_priority - приоритет реплики из БД добавляется напрямую к оценке
    \item App preferences - учёт пожеланий пользователя
\end{itemize}
Итоговый score - сумма этих слагаемых.

\paragraph{Что baseline оптимизирует и чего не делает.}
Штатный планировщик оптимизирует локальную выгоду для текущего RPC с жёстким требованием уложиться в дедлайн задачи. Он не стремится к равномерному распределению задач между хостами, не учитывает глобальную загрузку хостов, не различает классы устройств - только доступность конкретного хоста и его характеристики, не сопоставляя хосты между собой и с типами задач. Таким образом, возникает проблема: мощные хосты забирают любые задачи, которые им предлагает планироващик, а более слабым узлам достаются не самые простые с точки зрения требуемой вычислительной мощности задачи.

\subsection{Требования к кастомному алгоритму}

Исходя из обзора литературы, ограничений штатного планировщика BOINC и целей данной работы, к разрабатываемому алгоритму были сформулированы следующие требования:
\begin{enumerate}
    \item Минимальная инвазивность - сохранить весь контракт штатного scheduler: feeder, feasibility checks, replication, locking shared memory, обновление БД. Меняется только функция ранжирования допустимых кандидатов
    \item Size-aware dispatch - ключевая идея: точное сопоставление сложности задачи с производительностью узла для более честного распределения задач
    \item Churn-awareness - учёт динамической доступности узла, чтобы не отправлять тяжёлые задачи на малодоступные хосты
    \item Отсутствие миграции - не вводить перенос задач между хостами, поскольку это несовместимо с моделью BOINC и неоправданно дорого в гетерогенной нестабильной среде
    \item Минимизация накладных расходов - решение принимается за один проход без глобального мониторинга и без обращений к БД сверх штатных проверок
    \item Сравнимость - помимо целевой политики реализовать контрольные алгоритмы (random, LPT, SJF, Round Robin, Weighted Least Loaded) для сравнения качества распределения и накладных расходов
\end{enumerate}

\subsection{Разработка планировщика задач в гетерогенной системе}

Модификация выполнена в модуле sched\_send.cpp. При включенном feature flag - custom\_load\_balancer=1 - вместо send\_work\_score() вызывается send\_work\_custom(). Функция send\_work\_custom() повторяет структуру send\_work\_score():
\begin{itemize}
    \item Сканирование ssp->wu\_results[] со случайным offset
    \item Подбор app\_version и feasibility через те же get\_score(), wu\_is\_infeasible\_fast(), slow\_check()
    \item Сортировка кандидатов по score и отправка top-$N$
\end{itemize}
Отличие - в методе custom\_score(), которая заменяет штатный JOB::get\_score() для вычисления итоговой оценки хоста.

Основной идеей было взять за основу оценку baseline-алгоритма и дополнить ее членами, явно учитывающими размер задачи, доступность хоста и "соответствие" мощности хоста размеру задачи. Целевая политика - hybrid, остальные служат контрольными для изоляции отдельных гипотез.

\paragraph{Контрольные политики}
Все контрольные политики используют защищённый baseline score ($100 \times s^{\text{BOINC}}$), чтобы штатные факторы (reliability, locality) сохраняли влияние, а экспериментальный член мог их сдвинуть:
\begin{table}[H]
    \centering
    \caption{Реализованные политики dispatch}
    \footnotesize
    \begin{tabular}{p{2.4cm} p{8.8cm}}
        \toprule
        Политика & Суть ranking \\
        \midrule
        \texttt{baseline} & штатный send\_work\_score() \\
        \texttt{random} & baseline + детерминированный псевдослучайный шум от result\_id и host\_id \\
        \texttt{lpt} & baseline + $\log(1 + \hat{t}_{ij})$ - длинные задачи первыми \\
        \texttt{sjf} & baseline $-$ $\log(1 + \hat{t}_{ij})$ - короткие задачи первыми \\
        \texttt{round\_robin} & baseline + циклический бонус по result\_id mod 6 и host\_id \\
        \texttt{weighted\_least\_loaded} & baseline + $\log(1 + v_j \cdot a_j / (L_j + 1))$, где $L_j$ - число задач in-progress на хосте \\
        \texttt{hybrid} & кастомный score \\
        \bottomrule
    \end{tabular}
\end{table}
Здесь $v_j$ - host\_speed\_factor (число CPU у хоста), $a_j$ - cpu\_available\_frac.

\paragraph{Кастомная политика}
Для пары (workunit $i$, host $j$) вычисляется составной score. Сначала определяются вспомогательные величины:
\begin{align*}
    a_j &= \mathrm{clamp}(\text{cpu\_available\_frac}_j,\ 0.15,\ 1.0), \\
    \tilde{t}_{ij} &= \hat{t}_{ij} / a_j, \\
    \rho_{ij} &= \mathrm{clamp}(\tilde{t}_{ij} / T_{\text{target}},\ 0.01,\ 100),
\end{align*}
где $T_{\text{target}} = 30$ секунд - целевое время выполнения (параметр custom\_lb\_target\_runtime, близко к длительности medium-задач). Далее:
\begin{align*}
    \text{size\_affinity}_{ij} &= -|\log \rho_{ij}| \cdot a_j
        && \text{штраф за несоответствие размера задачи целевому runtime}, \\
    \text{deadline\_press}_i &= T_{\text{target}} / \text{delay\_bound}_i
        && \text{бонус срочным workunit}, \\
    \text{runtime\_penalty}_{ij} &= \log(1 + \tilde{t}_{ij} / T_{\text{target}})
        && \text{штраф за длинные задачи на текущем хосте}, \\
    \text{host\_fit}_{ij} &= (\log(1 + v_j) - \log(1 + \tilde{t}_{ij})) \cdot a_j^2
        && \text{бонус за соответствие мощности хоста длительности задачи}.
\end{align*}
Дополнительно вводится slow\_host\_long\_penalty - усиленный штраф за отправку medium/long задач на маломощные узлы, масштабируемый относительно $T_{\text{target}}$ и $v_j$.

Baseline score масштабируется с учётом доступности хоста, что ослабляет влияние reliability / locality на нестабильных хостах и усиливает на стабильных - важно для сценариев с отказами узлов.
\[
    s^{\text{base}}_{ij} = (25 + 55 \cdot a_j) \cdot s^{\text{BOINC}}_{ij},
\]

Итоговый score выглядит так:
\begin{align*}
    \text{score}_{ij} =\;& s^{\text{base}}_{ij}
        + w_{\text{size}} \cdot \text{size\_affinity}_{ij}
        + w_{\text{dl}} \cdot \text{deadline\_press}_i \\
        & - w_{\text{rt}} \cdot \text{runtime\_penalty}_{ij}
        + 0.05 \cdot w_{\text{size}} \cdot \text{host\_fit}_{ij}
        - w_{\text{rt}} \cdot \text{slow\_host\_long\_penalty}_{ij},
\end{align*}
Все веса задаются в config\.xml: $w_{\text{size}}=2$, $w_{\text{dl}}=5$, $w_{\text{rt}}=0.55$.

\paragraph{Интерпретация элементов score}
\begin{itemize}
    \item size\_affinity наказывает задачи, чьё спрогнозированное время работы сильно отличается от $T_{\text{target}}$, сильнее на малодоступных хостах - стимулирует более честное назначение задачи в текущем контексте
    \item host\_fit поощряет отправку задач на хосты, чья мощность $v_j$ согласована с $\tilde{t}_{ij}$: мощный хост + длинная задача или слабый + короткая
    \item runtime\_penalty и slow\_host\_long\_penalty не дают накапливать длинные задачи на маломощные узлы
    \item deadline\_press предотвращает голодание задач с коротким таймаутом
    \item Множитель $(25 + 55\cdot a_j)$ вместо $100$ у контрольных политик - компромисс: baseline-факторы BOINC сохраняют значимость, но кастомные слагаемые также могут играть важную роль при формировании финальной оценки хоста
\end{itemize}

\paragraph{Параметры конфигурации}
Переключение политик и весов выполняется через файл config.xml без пересборки:
\begin{itemize}
    \item custom\_load\_balancer - 0 (baseline) / 1 (custom)
    \item custom\_lb\_policy - имя политики
    \item custom\_lb\_target\_runtime, custom\_lb\_size\_weight, custom\_lb\_deadline\_weight, custom\_lb\_runtime\_weight
    \item max\_wus\_to\_send=1, max\_wus\_in\_progress=2 - ограничения стенда, исключающие захват всей очереди одним быстрым клиентом
\end{itemize}

\subsection{Подбор оптимальных параметров для алгоритма}


\subsection{Ограничения разработанного подхода}
\begin{itemize}
    \item Локальность решений - планировщик не видит глобального распределения задач между однородными хостами: они имеют схожий baseline score, поэтому возможна неравномерность распределения похожих задач мпежд такими хостами, что на самом деле не так и важно при сохранении схожей нагрузки на однородных узлах
    \item Зависимость от оценок - $\hat{t}_{ij}$ строится на rsc\_fpops\_est, которое может расходиться с реальным CPU-time
    \item Компромисс fairness vs makespan - усиление host\_fit и штрафов за long на слабых узлах улучшает равномерность и распределение по типам устройств, но увеличивает суммарное время работы относительно других политик, которые "сливают" мелкие задачи на кластеры и минимизирует продолжительность работы
    \item Нет миграции при churn - если хост перестал быть доступен с задачей in-progress, та ждёт таймаута и репликации; кастомный алгоритм лишь снижает вероятность отправки тяжёлых задач на нестабильные хосты до их назначения
\end{itemize}

Эвристики также заметно проигрывают по скорости работы планировщику "из коробки".
