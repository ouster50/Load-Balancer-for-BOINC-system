\section*{Аннотация}   % this is how to use russian
В работе исследуется выдача заданий в гетерогенной среде BOINC с помощью локального ранжирования задач при запросе клиента. Реализована эвристика hybrid, учитывающая оценку длительности задачи, условную мощность узла и статистику доступности BOINC. Создан тестовый контейнерный стенд из шести клиентов четырёх различных ресурсных профилей. В каждом сценарии выполнено сравнение штатного планировщика и шести экспериментальных политик на наборе синтетических заданий. Hybrid повышает значения индекса Jain по числу завершённых задач относительно baseline во всех шести основных сравнениях, а также превосходит его в метриках пропускной способности в нестабильной среде. Установлен компромисс между равномерностью числа задач, временем обработки их фиксированного набора и нагрузкой на узлы; описаны условия применимости результатов.

\section{Введение} 
\subsection{Описание предметной области}
Предметная область проекта охватывает распределенные системы с гетерогенной инфраструктурой с основными компонентами:
\begin{itemize}
    \item BOINC (Berkeley Open Infrastructure for Network Computing) — платформа для добровольных вычислений, объединяющая ресурсы разнородных устройств (серверов, кластеров, персональных компьютеров) в единую сеть
    \item Кластерные ресурсы — группа вычислительных узлов под общим управлением
    \item Гетерогенные ресурсы — устройства с различными характеристиками: вычислительной мощностью, объемом памяти, доступностью и другими
    \item Балансировщик нагрузки — компонент, отвечающий за распределение вычислительных задач между узлами с учетом их возможностей и текущих состояний
\end{itemize}
Также предметная область имеет следующие особенности:
\begin{itemize}
    \item Отсутствие централизованного контроля за узлами системы
    \item Разнородность ресурсов каждого из узлов
    \item Различные режимы работы узлов (не все устройства доступны на протяжении 100\% времени)
    \item Различный объем задач, время выполнения которых может варьироваться от нескольких минут до нескольких дней
    \item Необходимость минимизации накладных расходов для балансировщика
\end{itemize}

\subsection{Актуальность и значимость}
Актуальность данного проекта обусловлена множеством существующих на данный момент проблем, таких как:
\begin{enumerate}
    \item Современные вычислительные задачи такие, как анализ больших данных, биоинформатика, требуют огромного количества ресурсов, что способствует росту числа гетерогенных распределенных систем
    \item BOINC учитывает производительность, доступность и совместимость узлов, однако локальная выдача задач в ответ на запрос клиента не обеспечивает заданного глобального распределения нагрузки
    \item Необходимость развития динамических алгоритмов балансировки в противовес существующим решениям с их статическими правилами
    \item Исследование компромисса между скоростью выполнения набора заданий и распределением работы между разнородными клиентами
\end{enumerate}

\subsection{Цели и задачи}
Целью данного проекта является разработка системы выдачи заданий для распределенной системы на платформе BOINC. Для ее достижения необходимо было выполнить следующие задачи:
\begin{enumerate}
    \item Обзор систем балансировки нагрузки для кластеров и распределенных систем
    \item Выбор системы моделирования и адаптация модели под специфику гибридной распределенной системы
    \item Реализация/модификация системы балансировки нагрузки гибридной распределенной системы
    \item Тестирование системы балансировки на модели гибридной распределенной системы
    \item Анализ полученных результатов
\end{enumerate}

\subsection{Состав результатов проекта}
\begin{enumerate}
    \item Подробное описание методики моделирования гибридной распределенной системы
    \item Подробное описание системы балансировки нагрузки гибридной распределенной системы
    \item Анализ результатов моделирования системы
    \item Подготовка подробного отчета о проделанной работе и проведенном тестировании
\end{enumerate}

\section{Литературный обзор}
\subsection{Обзор предметной области}
Балансировка нагрузки отвечает за распределение работы между несколькими вычислительными ресурсами. Необходимо отличать маршрутизацию сетевых запросов от планирования длительных вычислительных заданий: для второго критически важны оценка трудоёмкости, ограничения ресурсов, сроки получения результата и доступность клиента-исполнителя. Поэтому классические методы серверной и облачной балансировки~\cite{srv-lb,lb-in-cloud} требуют адаптации к системе BOINC.

Статические методы используют заранее заданные правила, например циклический порядок или случайный выбор. Динамические методы используют сведения о текущем состоянии ресурсов; отдельные варианты допускают перенос работы, но миграция не является обязательным свойством динамического планирования~\cite{lb-in-ds}.

В BOINC разделены серверная выдача заданий, запрос работы клиентом и локальное планирование выполнения. Эти механизмы постоянно взаимодействуют между собой, поэтому результат серверной эвристики зависит также от частоты запросов и настроек клиента~\cite{boinc-platform}.

\subsection{Обзор существующих методов}
Рассмотрим методы балансировки нагрузки, применимые к распределённым вычислительным системам с акцентом на гибридные конфигурации (платформы типа BOINC + стабильные кластерные сегменты). Среди критериев для них можно выделить: простота мониторинга, устойчивость к churn (неконтролируемое подключение / отключение узлов), гетерогенность ресурсов, величина накладных расходов, масштабируемость. Всего можно выделить несколько групп подходов к балансировке нагрузки:

\begin{itemize}
    \item Классические статические методы (Round Robin, Random Strategy) — просты в мониторинге, однако не учитывают размер и время выполнения задач
    \item Классические динамические методы (Least Connections) — используют число соединений как приближение нагрузки и не учитывают вычислительную трудоёмкость заданий
    \item Адаптивные методы — балансировка происходит на основе метрик, вычисляемых в реальном времени; требуют постоянных вычислений
    \item Предиктивные ML-подходы — методы с обучаемой оценкой нагрузки; их качество зависит от обучающих данных и соответствия условий применения~\cite{lb-adv}
    \item Существующие решения для BOINC (CluBORun) — интеграция кластерных ресурсов вычисления~\cite{cluborun}
\end{itemize}

Большинство классических и оптимизационных алгоритмов работают при допущении, что узлы доступны и их характеристики относительно стабильны. В средах типа BOINC это допущение неприменимо: изменчивость системы и разнородность устройств приводят к частому перераспределению задач между узлами. Если в гомогенных системах перенос задач - относительно стандартный процесс, в гибридных системах такой подход может привести к серьёзному росту накладных расходов из-за неоднородности устройств, поэтому в подобных системах правильным подходом считается исключение или сведение к минимум подобных операций. Также нужно отметить, что для гибридных систем важно сохранять баланс между количеством собираемых метрик и их полезностью для планировщика, что труднодостижимо при подходах с глобальным мониторингом узлов.~\cite{lb-in-cloud}

\subsection{Особенности BOINC}
Платформа BOINC использует модель client-initiated: вычислительный узел сам запрашивает работу через RPC. Scheduler сканирует массив feeder, оценивает совместимость задач с хостом и ранжирует кандидатов по score. Назначенная задача не мигрирует на другой host до таймаута или повторной репликации. Поле $rsc\_fpops\_est$ задаёт оценку сложности, которая может расходиться с реальным временем выполнения - это важный источник ошибок для любой adaptive-политики. Решение CluBoRun~\cite{cluborun} интегрирует кластерные ресурсы в BOINC-проект, но не решает глобальную балансировку по классам устройств с учетом их мощности.

\section{Моделирование системы}

\subsection{Выбор способа моделирования}

Для проверки политик балансировки выбран локальный стенд на базе Docker Compose и реального планировщика BOINC~8.3.0, а не discrete-event симулятор или GPU-кластер. Такой выбор обусловлен следующими соображениями:
\begin{itemize}
    \item Сохраняется полный RPC-цикл BOINC (feeder, feasibility checks, replication, обновление БД)
    \item Результаты воспроизводимы через скрипты и конфигурационные файлы из артефактов каждого запуска
    \item Гетерогенность задаётся через Docker cgroup и BOINC preferences без покупки реальной группы устройств с реальным GPU
    \item Синтетическая нагрузка задаётся встроенным приложением для генерации задач с параметром $-cpu\_time$, отвечающим за нагрузку на процессор
\end{itemize}
Основной эксперимент - CPU-only: отсутствие физических устройств с собственным GPU не позволяет построить корректную модель, а варианты с разворачиванием виртуальных машин лишь имитируют наличие GPU.

\subsection{Топология системы}
Тестовый стенд состоит из 6 хостов-устройств с различными характеристиками:
\begin{itemize}
    \item 2 кластерных элемента (4 CPU, 4 GiB RAM)
    \item 1 устройство ПК (2 CPU, 2 GiB RAM)
    \item 1 маломощный узел (1 CPU, 1 GiB RAM)
    \item 2 элемента - мобильных устройств (0.5 CPU, 0.5 GiB RAM)
\end{itemize}

Каждое устройство представляет собой независимый вычислительный хост; с точки зрения технической реализации каждый хост - это отдельный Docker контейнер, который конфигурационно настроен под конкретное число CPU. Данный выбор хостов с их настройками был обусловлен следующими требованиями к тестовому стенду:

\begin{itemize}
    \item Стенд обязан содержать разнородные с точки зрения мощности устройства для моделирования гибридной среды
    \item Стенд обязан содержать как высокопроизводительные элементы (кластеры), так и низкопроизводительные (мобильные устройства)
    \item Стенд обязан иметь несколько одинаковых устройств для проверки балансировки нагрузки между однородными хостами (распределение задач между одинаковыми с точки зрения мощности клиентами)
\end{itemize}
Таким образом и была сформирована модель системы, используемая при тестировании.

\paragraph{Протокол churn}
Отказы моделируются через docker compose pause/unpause на всех шести клиентах с рассинхронизацией старта (разница в начале циклов отказа конфигурируется через $CHURN\_STAGGER\_SECONDS$). Каждый хост проходит несколько циклов online $\rightarrow$ pause $\rightarrow$ unpause. Доля offline в одном цикле:
\[
    f_{\text{off}} = \frac{T_{\text{offline}}}{T_{\text{online}} + T_{\text{offline}}}.
\]
Например, при 25/12 получаем $f_{\text{off}} \approx 32\%$, при 40/10 - 20\%, при 12/25 - 68\%. Все события (включение / отключение хоста) логгируются для последующего вычисления метрики Load CV.

\paragraph{Допущения тестового стенда}
Все шесть клиентов используют одну физическую машину и упрощённую сеть. CPU-квоты Docker и настройки BOINC моделируют ограничения ресурсов, но не различные микроархитектуры процессоров. Ограничения $max\_wus\_to\_send=1$ и $max\_wus\_in\_progress=2$ ограничивают захват очереди задач более быстрыми хостами. Эти допущения не отменяют A/B-сравнение политик на одном стенде, однако не позволяют напрямую экстраполировать абсолютные значения метрик на production систему.

\section{Подходы к тестированию системы и метрики качества}

\subsection{Эвристики распределения задач}

В качестве контрольных эвристик в проекте реализованы:
\begin{itemize}
    \item LPT (Longest Processing Time first) - приоритет длинным задачам; проверяется гипотеза о сокращении общего времени завершения набора
    \item SJF (Shortest Job First) - приоритет коротким задачам; проверяется гипотеза о снижении среднего времени отклика, при этом крупные задачи могут простаивать в очереди дольше
\end{itemize}

Slurm и Torque работают в другой модели управления ресурсами и не включены в экспериментальное сравнение: их полноценная интеграция потребовала бы другого стенда, а также они неприменимы к гетерогенной структуре BOINC. На стенде сравниваются baseline, hybrid и локальные реализации эвристик random, LPT, SJF, Round Robin и Weighted Least Loaded.

\subsection{Метрики оценки производительности}

Выбор метрик обусловлен необходимостью учета как общих показателей производительности, так и особенностей гетерогенной вычислительной среды.

\begin{itemize}
    \item Пропускная способность (Throughput) - число выполненных задач за единицу времени. Формула: $T = \dfrac{N_{\text{completed}}}{\Delta t}$, где $\Delta t$ - время от начала выполнения задач до его окончания
    \item Загруженность узлов - для узла $j$: $u_j = \dfrac{\text{cpu\_time}_j}{\text{online\_seconds}_j \cdot \text{ncpus}_j}$. Сводная метрика - Load CV $= \sigma(u_j)/\bar{u}$ - коэффициент вариации CPU-нагрузки; может расходиться с Jain
    \item Общая продолжительность выполнения задач - $Makespan = \max_i t_{\text{finish}}^{(i)} - \min_i t_{\text{create}}^{(i)}$
    \item Равномерность числа завершённых задач (Jain) - $J = \dfrac{(\sum_i x_i)^2}{n\sum_i x_i^2}$, где $x_i$ - число завершённых задач на хосте $i$; в расчёт попадают только хосты с $x_i \geq 1$
    \item Response - время от создания задачи до получения результата сервером; p95 - 95-й перцентиль
\end{itemize}

Такой набор метрик позволяет оценить и скорость системы (throughput, makespan, response), и качество распределения (Jain, Load CV). Отдельно анализируется согласованность типов задач с классами устройств (таблицы short/medium/long по хостам).

\section{Разработка алгоритма балансировки}

Прежде чем описывать разработанный алгоритм, необходимо зафиксировать, как именно работает штатный планировщик в BOINC, поскольку именно он выступает baseline в экспериментах и служит границей, ниже которой по метрикам опускаться неприемлемо.

\subsection{Планировщик BOINC по умолчанию}

BOINC использует pull-модель распределения задач: вычислительный узел самостоятельно инициирует RPC-запрос к планировщику и сообщает, сколько работы он готов принять (в секундах CPU, в числе задач или иначе). Планировщик не выбирает хост для задачи - он лишь отвечает на запрос данного клиента в данный момент. Назначенная задача не мигрирует на другой узел по достижении таймаута, при ошибке или при создании новой реплики. Это принципиально отличает BOINC от централизованных кластерных планировщиков (Slurm, Torque), где планировщик видит всю очередь задач и все узлы одновременно, и именно эти недостатки должны быть устранены или сведены к минимуму в рамках текущего проекта.

Очередь задач, доступная планировщику, - это не вся база данных, а кэш в памяти, который заполняет отдельный процесс под названием feeder. Он читает из БД информацию о задачах, готовых к отправке, и помещает их в массив фиксированного размера (по умолчанию до 100 слотов, параметр $shmem\_work\_items$ задаётся конфигурационно). Каждый элемент содержит метаданные задачи (оценку сложности $rsc\_fpops\_est$, требования к памяти и диску), приоритет реплики $res\_priority$ и счётчик отказов $infeasible\_count$. Планировщик при каждом запросе клиента сканирует этот массив; порядок обхода начинается со случайного смещения, чтобы не застревать на одних и тех же задачах.

Для выбора задач текущему хосту в выбранной конфигурации вызывается функция $send\_work\_score()$, логика которой сводится к двум шагам:
\begin{enumerate}
    \item Сканирование и ранжирование - для каждого слота в shared memory подбирается совместимая версия приложения под платформу хоста, для каждой допустимой пары $(workunit, host)$ вычисляется score, после чего все кандидаты сортируются по score по убыванию
    \item Отправка - планировщик последовательно пытается выдать задачи из отсортированного списка, пока не исчерпан лимит RPC $max\_wus\_to\_send$, не превышены квоты $max\_jobs\_in\_progress$ и пока хост ещё запрашивает работу
\end{enumerate}
Отдельный проход выполняется для каждого типа процессора (GPU-типы, затем CPU).

Перед выдачей проверяется допустимость задания для хоста:
\begin{itemize}
    \item Достаточно ли оперативной памяти и дискового пространства?
    \item Приложение входит в список, выбранный пользователем (хостом) в project preferences?
    \item Хост успеет завершить задачу до глобального дедлайна по ней?
\end{itemize}
Последняя проверка - ключевая для гетерогенной среды. Оценка длительности выполнения задачи:
\[
    \hat{t}_{ij} = \frac{\text{rsc\_fpops\_est}_i}{\text{projected\_flops}_j \cdot \text{available\_frac}_j},
\]
Где $available\_frac$ - доля времени, когда клиент статистически доступен для BOINC. К этой оценке добавляется $estimated\_delay$ - время, которое хост уже занят текущими задачами. Если $\hat{t}_{ij} + \text{estimated\_delay} > \text{delay\_bound}$, задача для данного хоста в score не попадает. Следствие: мощные и стабильные узлы забирают длинные задачи; слабые и малодоступные - только короткие или остаются без задач.

Если быстрые проверки пройдены, выполняется slow\_check() с запросами в БД: нет ли уже результата этой задачи на данном хосте. Только после этого задача добавляется в ответ клиенту.

Оценка каждого хоста считается исходя из нескольких эвристик:
\begin{itemize}
    \item Reliability - при требовании надёжности проверяется признак reliable соответствующей версии приложения на хосте
    \item LTT - для $high-priority workunits$ в режиме $batch acceleration$ задачи идут только на LTT-хосты
    \item Locality - бонус, если входные данные задачи уже есть на хосте
    \item $res\_priority$ - приоритет реплики из БД добавляется напрямую к оценке
    \item App preferences - учёт пожеланий пользователя
\end{itemize}
Из этих факторов и складывается итоговый score.

\paragraph{Что baseline оптимизирует и чего не делает.}
Штатный планировщик оптимизирует локальную выгоду для текущего RPC клиента. При этом он не учитывает глобальную загрузку хостов, не различает классы устройств - только доступность конкретного хоста и его характеристики. Таким образом, возникает проблема: мощные хосты забирают любые задачи, которые им предлагает планировщик, а более слабым узлам достаются не самые простые с точки зрения требуемой вычислительной мощности задачи, из-за чего те вынуждены простаивать.

\subsection{Требования к кастомному алгоритму}

Исходя из обзора литературы, ограничений штатного планировщика BOINC и целей данной работы, к разрабатываемому алгоритму были сформулированы следующие требования:
\begin{enumerate}
    \item Минимальная инвазивность - сохранить весь контракт штатного scheduler: feeder, feasibility checks, replication, locking shared memory, обновление БД. Меняется только функция ранжирования допустимых кандидатов
    \item $Size-aware dispatch$ - ключевая идея: эвристическое сопоставление оценки размера задачи с ресурсным профилем узла
    \item $Churn-awareness$ - учёт динамической доступности узла, чтобы не отправлять тяжёлые задачи на малодоступные хосты
    \item Отсутствие миграции - не вводить перенос задач между хостами, поскольку такая возможность потребовала бы отдельного механизма переноса состояния приложения
    \item Минимизация накладных расходов - сканирование кэша и сортировка кандидатов без введения глобального мониторинга; при $M$ слотах и $K$ кандидатах сложность ранжирования составляет $O(M+K\log K)$
    \item Сравнимость - помимо целевой политики реализовать контрольные алгоритмы (random, LPT, SJF, Round Robin, Weighted Least Loaded) для сравнения качества распределения и накладных расходов
\end{enumerate}

\subsection{Разработка планировщика задач в гетерогенной системе}

Основная реализация находится в $sched\_custom\_load\_balancer.cpp$, переключение режима выполняется в $sched\_send.cpp$. При включённом флаге вместо встроенной вызывается функция $send\_work\_custom()$, которая повторяет структуру оригинальной $send\_work\_score()$:
\begin{itemize}
    \item Сканирование $ssp->wu\_results[]$ со случайным offset
    \item Подбор $app\_version$ и $feasibility$ через те же методы $get\_score()$, $wu\_is\_infeasible\_fast()$, $slow\_check()$
    \item Сортировка кандидатов по score и отправка top-$N$
\end{itemize}
Отличие - в методе custom\_score(), который заменяет штатный JOB::get\_score() для вычисления итоговой оценки хоста.

Поскольку Docker-клиенты часто сообщают одинаковый $p\_fpops$, для hybrid введён коэффициент $host\_speed\_factor$ = $v_j$ по числу CPU узла. Спрогнозированное время в этом случае: $\hat{t}_{ij} = \text{estimate\_duration}(i,j) / v_j$.

Основной идеей было взять за основу оценку baseline-алгоритма и дополнить ее членами, явно учитывающими размер задачи, доступность хоста и "соответствие" мощности хоста размеру задачи. Целевая политика - hybrid, остальные служат контрольными для изоляции отдельных гипотез.

\paragraph{Контрольные политики}
Все контрольные политики используют защищённый $baseline$ score ($100 \times s^{\text{BOINC}}$), чтобы штатные факторы ($reliability$, $locality$) сохраняли влияние, а экспериментальный член мог их сдвинуть:
\begin{table}[H]
    \centering
    \caption{Реализованные политики}
    \footnotesize
    \begin{tabular}{ll}
        \toprule
        Политика & Суть ранжирования \\
        \midrule
        \texttt{baseline} & штатный send\_work\_score() \\
        \texttt{random} & baseline + детерминированный псевдослучайный шум от $result\_id$ и $host\_id$ \\
        \texttt{lpt} & baseline + $\log(1 + \hat{t}_{ij})$ - длинные задачи первыми \\
        \texttt{sjf} & baseline $-$ $\log(1 + \hat{t}_{ij})$ - короткие задачи первыми \\
        \texttt{round\_robin} & baseline + циклический score по $result\_id$ mod 6 и $host\_id$ \\
        \texttt{weighted\_least\_loaded} & baseline + $\log(1 + v_j \cdot a_j / (L_j + 1))$, где $L_j$ - число задач in-progress на хосте \\
        \texttt{hybrid} & кастомный score \\
        \bottomrule
    \end{tabular}
\end{table}
Здесь $v_j$ - host\_speed\_factor (число CPU у хоста), $a_j$ - cpu\_available\_frac.

\paragraph{Кастомная политика}
Для пары (workunit $i$, host $j$) вычисляется составной score. Сначала определяются вспомогательные величины:
\begin{align*}
    a_j &= \mathrm{clamp}(\text{cpu\_available\_frac}_j,\ 0.15,\ 1.0), \\
    \tilde{t}_{ij} &= \hat{t}_{ij} / a_j, \\
    \rho_{ij} &= \mathrm{clamp}(\tilde{t}_{ij} / T_{\text{target}},\ 0.01,\ 100),
\end{align*}
где $T_{\text{target}} = 30$ секунд - целевое время выполнения (параметр $custom\_lb\_target\_runtime$, близко к длительности medium-задач). Далее:
\begin{itemize}
    \item $size\_affinity_{ij} = -|\log \rho_{ij}| \cdot a_j$ - штраф за несоответствие размера задачи целевому runtime
    \item $deadline\_press_i = T_{\text{target}} / \text{delay\_bound}_i$ - бонус срочным задачам
    \item $runtime\_penalty_{ij} = \log(1 + \tilde{t}_{ij} / T_{\text{target}})$ - штраф за длинные задачи на текущем хосте
    \item $host\_fit_{ij} = (\log(1 + v_j) - \log(1 + \tilde{t}_{ij})) \cdot a_j^2$ - бонус за соответствие мощности хоста длительности задачи
\end{itemize}
Дополнительный штраф $P_{ij}=\texttt{slow\_host\_long\_penalty}$ задан явно:
\[
P_{ij}=\begin{cases}
1.5\cdot\dfrac{\hat t_{ij}}{T_{\mathrm{target}}}\cdot\dfrac{2-v_j}{a_j},
 & T_{\mathrm{target}}\ge\hat t_{ij}>T_{\mathrm{target}}/2,\ v_j<2\\[3pt]
0.5\cdot\left(\dfrac{\hat t_{ij}}{T_{\mathrm{target}}}-1\right)\cdot\dfrac{4-v_j}{a_j},
 & \hat t_{ij}>T_{\mathrm{target}},\ 2\leq v_j<4\\[3pt]
0, & \text{иначе}.
\end{cases}
\]

Baseline score масштабируется с учётом доступности хоста, что ослабляет влияние $reliability$ / $locality$ на нестабильных хостах и усиливает на стабильных - важно для сценариев с отказами узлов:
\[
    s^{\text{base}}_{ij} = (10 + 10 \cdot a_j) \cdot s^{\text{BOINC}}_{ij},
\]

Итоговый score выглядит так:
\begin{align*}
    \text{score}_{ij} =\;& s^{\text{base}}_{ij}
        + w_{\text{size}} \cdot \text{size\_affinity}_{ij}
        + w_{\text{dl}} \cdot \text{deadline\_press}_i \\
        & - w_{\text{rt}} \cdot \text{runtime\_penalty}_{ij}
        + 0.05 \cdot w_{\text{size}} \cdot \text{host\_fit}_{ij}
        - w_{\text{rt}} \cdot \text{slow\_host\_long\_penalty}_{ij},
\end{align*}
Веса задаются в config.xml: $w_{\text{size}}=2$, $w_{\text{dl}}=5$, $w_{\text{rt}}=0.55$.

\paragraph{Интерпретация элементов score}
\begin{itemize}
    \item $size\_affinity$ предпочитает эффективные задачи, по времени выполнения близкие к $T_{\mathrm{target}}$. При фиксированном $\rho$ модуль штрафа уменьшается, но сама $\rho$ также зависит от доступности.
    \item В текущем RPC $v_j$ постоянно: слагаемое $\log(1+v_j)$ внутри host\_fit не меняет порядок задач. Переменная часть host\_fit предпочитает меньшую длительность; соответствие крупных задач мощным узлам задаётся совокупностью членов, прежде всего size\_affinity и $P_{ij}$.
   \item $runtime\_penalty$ и $slow\_host\_long\_penalty$ не дают накапливать длинные задачи на маломощные узлы
    \item $deadline\_press$ предотвращает долгое ожидание взятия в работу для задач с коротким таймаутом
    \item Множитель $(10 + 10\cdot a_j)$ вместо $100$ у контрольных политик - компромисс: baseline-факторы BOINC сохраняют значимость, но кастомные слагаемые также могут играть важную роль при формировании финальной оценки хоста
\end{itemize}

\paragraph{Параметры конфигурации}
Переключение политик и весов выполняется через файл config.xml без пересборки:
\begin{itemize}
    \item $custom\_load\_balancer$ - 0 (baseline) / 1 (custom)
    \item $custom\_lb\_policy$ - имя политики
    \item $custom\_lb\_target\_runtime$ - целевая длительность
    \item $custom\_lb\_size\_weight$ - вес соответствия размера
    \item $custom\_lb\_deadline\_weight$ - вес срока возврата
    \item $custom\_lb\_runtime\_weight$ - вес штрафов длительности
    \item $max\_wus\_to\_send=1$, $max\_wus\_in\_progress=2$ - ограничение числа выдаваемых задач
\end{itemize}

\subsection{Подбор оптимальных параметров для алгоритма}

Веса кастомного алгоритма ($w_{\text{size}}=2$, $w_{\text{dl}}=5$, $w_{\text{rt}}=0.55$, $T_{\text{target}}=30$~s) подбирались итеративно по серии прогонов baseline vs hybrid в нестабильной среде с отказами до получения устойчивого преимущества hybrid по равномерности распределения задач при приемлемой потере в общей продолжительности работы и пропускной способности. Ключевые решения:
\begin{itemize}
    \item Установка множителя baseline в значение $(10 + 10\cdot a_j)$ - кастомные слагаемые получают влияние на оценку, но уже посчитанный внутри BOINC score не обнуляется, поскольку цель проекта модифицировать текущую систему, а не написать с нуля. Увеличение коэффициента приводит к слишком высокой корреляции между обеими политиками; излишнее уменьшение - к минимизации вклада в итоговую сумму и как следствие потере смысла. Оптимальным по метрикам оказался коэффициент от 15 до 30 (при фиксированных остальных параметрах), после выявления которого была добавлена привязка к доступности - решение для более качественного учета churn
    \item $T_{\text{target}}=30$~s - получилось сопоставимо с длительностью medium-задач. Увеличение или уменьшение приводило к нарушению равномерности распределения задач между хостами и заметно ухудшало Jain
    \item $w_{\text{rt}}=0.55$ - баланс между штрафом тяжелых задач на слабых хостах и допустимым makespan
    \item Увеличение $w_{\text{size}}$ или $w_{\text{rt}}$ на 30-50\% повышает Jain, однако увеличивает makespan на 5-15\%, уменьшение же возвращает поведение к baseline
\end{itemize}

Исходя из изложенного выше, были зафиксированы параметры для алгоритма, после чего тот стал готов к полноценному тестированию.

\subsection{Ограничения разработанного подхода}
\begin{itemize}
    \item Локальность решений - планировщик не видит глобального распределения задач между однородными хостами: они имеют схожий baseline score, поэтому возможна неравномерность распределения похожих задач между такими хостами, что на самом деле не так и важно при сохранении схожей нагрузки на однородных узлах
    \item Зависимость от оценок - $\hat{t}_{ij}$ строится на $rsc\_fpops\_est$, которое может расходиться с реальным CPU-time
    \item Компромисс Jain vs makespan - усиление $host\_fit$ и штрафов за большие задачи на слабых узлах улучшает равномерность и распределение по типам устройств, но увеличивает суммарное время работы относительно других политик, которые в основном распределяют мелкие задачи на кластеры и минимизируют продолжительность работы
    \item Нет миграции при churn - если хост перестал быть доступен с задачей in-progress, та ждёт таймаута и репликации; кастомный алгоритм лишь снижает вероятность отправки тяжёлых задач на нестабильные хосты до их назначения
\end{itemize}

\subsection{Результаты экспериментов}
\begin{itemize}
    \item Baseline является хорошей базой, которая обходит (на 5-10\%) большинство классических эвристик по скорости и нагрузке на хосты
    \item LPT показал неожиданно хороший результат, сопоставимый с baseline, иногда даже обходя его по пропускной способности, а также оптимален по распределению нагрузки на узлы почти во всех сценариях, что можно объяснить наличием на тестовом стенде элементов кластеров - высокопроизводительных узлов, которые забирали долгие задачи на себя
    \item Классические подходы Round Robin и Weighted Least Loaded ожидаемо не показали достойного результата, сильно проигрывая всем политикам на 10-20\% по основным метрикам качества, что объясняется простотой их алгоритмов и отсутствием анализа гетерогенности системы
    \item SJF показал средний результат, иногда проигрывая классическим политикам из-за смещения фокуса на легкие задачи, тогда как при планировании важна комплексная оценка всего набора
    \item Разработанный алгоритм hybrid оказался одним из лучших по распределению задач между хостами (стабильно превышая подавляющее большинство политик по этому признаку на 5-15\%), что привело к увеличению коэффициента вариации нагрузки на узлы как компромисс. По остальным метрикам разработанный алгоритм оказался лучше baseline на 5-10\%: по общей продолжительности выполнения задач, по пропускной способности, по среднему времени нахождения задачи в очереди
\end{itemize}

Таким образом, эксперименты подтвердили поставленную в главе 5 гипотезу, что разработанный алгоритм лучше показывает себя в гибридной среде, чем baseline, и значительно более равномерно распределяет задачи между вычислительными узлами.

\section{Заключение}
В ходе работы разработан прототип системы выдачи заданий для гетерогенной среды BOINC. Предложенная эвристика hybrid учитывает оценку длительности задачи, условную вычислительную мощность узла и статистику его доступности. Модификация сохраняет pull-модель BOINC и штатные проверки допустимости заданий, изменяя их ранжирование при запросе клиента. Для оценки подхода создан контейнерный стенд и проведено сравнение со штатным планировщиком и контрольными эвристиками.

\subsection{Результаты}
\begin{enumerate}
    \item Рассмотрены существующие методы балансировки нагрузки и особенности их применения в BOINC. Выбран способ моделирования на основе Docker Compose и реальных компонентов BOINC, позволяющий исследовать выдачу задач разнородным клиентам при контролируемых изменениях доступности
    \item Реализованы шесть экспериментальных политик: random, lpt, sjf, weighted\_least\_loaded, round\_robin и hybrid. Вместе со штатной политикой baseline они протестированы на стенде из шести хостов четырёх ресурсных профилей. Сравнение выполнено в стабильной среде и пяти сценариях с периодической недоступностью клиентов на наборе из синтетических заданий
    \item По приведённым результатам hybrid обеспечивает более равномерное число завершённых задач между хостами, чем baseline, во всех шести сценариях: индекс Jain составляет от 0.871 до 0.923. В рассмотренных распределениях все длинные задачи выполняются кластерными узлами, а мобильные клиенты получают только короткие задания. Это соответствует поставленной задаче учитывать размер задания и ресурсный профиль клиента
    \item Во всех пяти рассмотренных сценариях с отказами hybrid сокращает общее время выполнения относительно baseline примерно на 5-10\%. В частности, при недоступности около 10\% продолжительность обработки очереди задач уменьшается с 250 до 226~с. В стабильной среде преимущество по скорости не достигается: общее время увеличивается с 252 до 268~с, также негативно влияя на равномерность загрузки узлов
\end{enumerate}

\subsection{Ограничения и компромиссы}
\begin{itemize}
    \item Равномерность числа задач не равнозначна равномерности вычислительной нагрузки: задания различаются по типу, а узлы - по мощности. Во всех смоделированных сценариях у hybrid выше коэффициент вариации нагрузки на узлы, чем у baseline, поэтому улучшение индекса Jain не означает улучшения всех характеристик балансировки
    \item Локальное ранжирование в pull-модели не обеспечивает глобального оптимального распределения и равномерной выдачи однотипных задач между равнозначными узлами. Уже назначенные задачи в тестовой модели не мигрируют между узлами, а их разнообразие сильно ограничено особенностями стенда
    \item Эксперименты ограничены шестью контейнерами на одной физической машине, упрощённой сетью и небольшим синтетическим набором CPU-задач. Периодическая приостановка контейнеров моделирует временную недоступность, но не охватывает всё разнообразие отказов реальной добровольной вычислительной среды
    \item Параметры эвристики подобраны для выбранного стенда и нагрузки. Полученные результаты не содержат оценки статистической значимости различий и не доказывают универсального превосходства hybrid. Для проверки устойчивости эффекта необходимы более обширные и разнообразные наборы заданий и эксперименты на физических устройствах
\end{itemize}

Таким образом, цель работы достигнута: система выдачи заданий разработана, реализована и протестирована в различных сценариях доступности узлов. На выбранном тестовом стенде продемонстрирована возможность улучшить распределение задач по ресурсным профилям и сократить время их обработки при частичной недоступности клиентов. Дальнейшее развитие подхода может быть связано с уточнением оценок, адаптацией параметров и проверкой результатов на более масштабной гетерогенной инфраструктуре.
